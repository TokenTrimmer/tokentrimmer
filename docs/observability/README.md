# Observability — traces, correlation, and integration boundaries

The gateway emits an OpenTelemetry span per request (`http_request`, created at
the request-entry middleware — `crates/core/src/middleware/trace.rs`). When the
cost is known (end of request, alongside the `x-tokentrimmer-*` response
headers) the chat and embeddings handlers record the OpenTelemetry **GenAI
semantic-convention** attributes plus TokenTrimmer **cost** attributes onto that
span (`crates/telemetry/src/gen_ai.rs`, called from
`crates/core/src/routes/chat.rs` and `crates/core/src/routes/embeddings.rs`).
The chat path stamps the attributes on every served outcome — non-streaming
miss, streaming miss, L1/L2 cache hit, and the streaming/fake-stream L1 hit — so
streaming and cache-hit traffic are not undercounted. Spans export over OTLP when
`OTEL_EXPORTER_OTLP_ENDPOINT` is set.

That environment variable configures one **process-wide, operator-owned**
OTLP/HTTP exporter for the running self-hosted gateway. It is not a hosted,
per-organization exporter. The Cloud control plane can store an organization
destination and encrypted headers, and its Dashboard can stage that row in a
disabled state, but the public gateway does not read those rows yet.

## Attributes emitted on the `http_request` span

GenAI semconv (`gen_ai.*`):

| Attribute | Meaning |
| --- | --- |
| `gen_ai.system` | Provider (`openai`, `anthropic`, `gcp.gemini`, `groq`, `mistral_ai`, …). |
| `gen_ai.provider.name` | Newer semconv spelling of `gen_ai.system`; emitted with the same value for forward-compat. |
| `gen_ai.operation.name` | `chat` on `/v1/chat/completions`, `embeddings` on `/v1/embeddings`. |
| `gen_ai.request.model` | Model the caller asked for (pre-routing). |
| `gen_ai.response.model` | Model that actually served the request (post-routing / failover). |
| `gen_ai.usage.input_tokens` | Prompt tokens. |
| `gen_ai.usage.output_tokens` | Completion tokens. |

TokenTrimmer cost (`tokentrimmer.*`), mirroring the `x-tokentrimmer-*` headers
— the same per-request values `compute_cost` produced (not recomputed):

| Attribute | Mirrors header |
| --- | --- |
| `tokentrimmer.cost_usd` | `x-tokentrimmer-cost-usd` — observed served usage priced from the active catalog; not provider-invoice reconciliation. |
| `tokentrimmer.baseline_cost_usd` | `x-tokentrimmer-baseline-cost-usd` — cost with no TokenTrimmer. |
| `tokentrimmer.saved_usd` | `x-tokentrimmer-saved-usd` — TokenTrimmer-attributed savings. |
| `tokentrimmer.provider_cache_saved_usd` | `x-tokentrimmer-provider-cache-saved-usd` — provider-side cache discount. |
| `tokentrimmer.cache` | `x-tokentrimmer-cache` — cache outcome (`hit-l1`, `hit-l2`, `miss`, `none`). |
| `tokentrimmer.route` | `x-tokentrimmer-route-matched` — matched route name (when routing applied). |
| `tokentrimmer.trace_id` | `x-tokentrimmer-trace-id` — the gateway's request-correlation UUID used by request logs and receipts. This is not the W3C/OpenTelemetry trace ID. |

## Correlation: two identifiers with different jobs

Every gateway response carries `X-TokenTrimmer-Trace-Id`, a UUID generated by
TokenTrimmer. The gateway records that exact value as
`tokentrimmer.trace_id` on its exported request span. The Python callbacks and
TypeScript Vercel adapter copy the same response value onto their active
application span. Use it to join an external span to TokenTrimmer request logs
and eligible receipts.

The OpenTelemetry/W3C trace ID is separate. A valid inbound `traceparent`
continues the caller's distributed trace and preserves `tracestate`; an absent
or malformed value starts a fresh trace. TokenTrimmer does not replace the W3C
trace ID with its response UUID, and the current gateway does not inject
`traceparent` on outbound provider requests.

## What exports today

| Source | Current behavior | Configuration owner |
| --- | --- | --- |
| Self-hosted gateway | Exports locally generated process spans over OTLP/HTTP protobuf to one endpoint when `OTEL_EXPORTER_OTLP_ENDPOINT` is set. | Gateway operator |
| Python LangChain/LangGraph | `TokenTrimmerCostCallback` adds response-derived `gen_ai.*` and `tokentrimmer.*` attributes to the active application span. | Application tracer/exporter |
| Python LiteLLM | `TokenTrimmerLiteLLMLogger` adds the same attributes after LiteLLM exposes the gateway response headers. | Application tracer/exporter |
| TypeScript Vercel AI SDK | `TokenTrimmerRunCost` or `recordTokenTrimmerCost` adds the shared attributes to a supplied or active span. | Application tracer/exporter |
| Hosted organization destination row | Stored and redacted by the Cloud control plane; Dashboard writes are forced to `enabled=false`. It is not consumed by the gateway. | Not an active exporter |

The SDK integrations annotate a span; they do not install or select a tracer
provider, exporter, Langfuse project, or LangSmith workspace. See the
[Python SDK callback examples](../../sdk-python/README.md#langchain-cost-callback--opentelemetry-spans)
and the
[TypeScript Vercel adapter example](../../sdk-typescript/README.md#framework-integrations-costsavings-into-otel-spans).

## Combined deployment patterns

These patterns preserve one system of record for prompt/trace operations while
using TokenTrimmer as the cost-policy, routing, and receipt layer:

1. **Self-hosted gateway + an OTLP-capable collector/backend.** Point the
   gateway's single operator endpoint at your collector. The collector may
   forward those spans to Tempo or another backend, including a Langfuse or
   LangSmith deployment only when that product's current configuration supports
   the chosen OTLP path. TokenTrimmer supplies the attributes above; collector
   routing, credentials, retention, and delivery monitoring stay with the
   operator.
2. **LangChain/LangGraph + LangSmith + TokenTrimmer.** Keep the application's
   normal LangSmith tracing for runs and evaluations. Add
   `TokenTrimmerCostCallback` to recover the gateway response metadata and
   annotate the active OpenTelemetry span. TokenTrimmer does not create or
   mutate LangSmith runs, import LangSmith evaluations, or generate LangSmith
   deep links.
3. **Vercel AI SDK or Python callbacks + Langfuse + TokenTrimmer.** Keep
   Langfuse instrumentation as the prompt/trace layer and invoke the matching
   TokenTrimmer adapter after the gateway response. The adapter records the
   shared cost/correlation attributes only when an OpenTelemetry span is active.
   It does not configure Langfuse ingestion, create scores/datasets, or prove
   that Langfuse retained the span.

These are composition boundaries, not end-to-end vendor certifications. Verify
the current vendor exporter instructions and data handling before production
use.

## Not implemented

- Hosted per-organization OTLP fanout, header rotation delivery, or a
  reachability/authentication test.
- Langfuse- or LangSmith-specific exporter presets and trace deep links.
- Evaluation, score, dataset, or annotation import into TokenTrimmer quality
  gates.
- Collector delivery, ingestion, retention, alerting, or production SLO
  evidence.

## Dashboard

`grafana-tokentrimmer-gateway.json` is an importable Grafana dashboard with
panels for request rate, p50/p95 latency, spend over time, savings, cache hits
by layer, cache-hit rate, and tokens by model.

The panels query the `http_request` span attributes above through a **Tempo**
(or any TraceQL-metrics-capable) trace data source, using TraceQL metrics
queries (`rate()`, `quantile_over_time`, `sum_over_time`, `count_over_time`).
On import, Grafana prompts for the Tempo data source (`DS_TEMPO`); the dashboard
also exposes a `${tempo}` data-source template variable so you can switch
sources without editing panels.

Import: Grafana → Dashboards → New → Import → upload the JSON, then pick your
Tempo data source. Requires Grafana 11+ and a Tempo backend with TraceQL
metrics enabled (it ingests the OTLP spans the gateway exports).
