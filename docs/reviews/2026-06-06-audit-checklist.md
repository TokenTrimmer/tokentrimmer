- [x] **🔴 [security] Audit chain has no signed tip/length — truncation of recent entries is undetectable** `(pub-auth-telemetry)`  **✅ DONE in #68 (2026-06-07).**
  - **Where:** public/crates/telemetry/src/audit/mod.rs:199-266 (verify_chain); audit/postgres.rs:55-159 (write)
  - **Issue:** verify_chain only validates that each entry links to the previous one (prev_hash) and that every present entry's hash+signature are valid. Nothing covers the chain *length* or the *tip*. An attacker (or insider) with DB write access who deletes the most recent N entries for an org leaves a chain that still verifies perfectly — the new last entry is a valid, signed entry, and there is no signed counter, no signed 'tip' record, and no anchor to detect that entries beyond it ever existed. The same applies to deleting an entire org's chain (verify_chain over an empty slice returns Ok). `seq` exists in the row but is excluded from canonical_payload_bytes (mod.rs:143-155), so seq is neither hashed nor signed and cannot be used to detect gaps. This undermines the core tamper-evidence promise ('tamper-evident record of every privileged action', keys.rs:457-458).
  - **Action:** Include `seq` in PayloadFields/canonical_payload_bytes so a deleted-and-renumbered entry breaks the hash, and add a periodically-signed checkpoint (org_id, max_seq, tip_hash, timestamp) anchored externally (e.g. emitted to logs/object store or co-signed) so verify_chain can assert the expected tip and length. At minimum, have verify_chain accept an expected_tip_seq/tip_hash argument and document that an empty chain for an org with known activity is a failure. (Note: post-scale-s3-object-lock WORM storage is the deferred long-term answer, but a signed seq is cheap now.)
  - **Verified:** Confirmed against the actual code. verify_chain (mod.rs:199-266) only checks, per entry: (1) prev_hash linkage to the previous entry (genesis = 64 zeros), (2) recomputed BLAKE3 hash equals stored hash, (3) Ed25519 signature over the raw hash. It has NO check on chain length, no signed tip record, and no external anchor. Over an empty slice the for-loop never runs and it returns Ok(()) (line 265). Therefore: (a) deleting the most recent N entries leaves a contiguous, perfectly-verifying prefix — entry 0 still links to genesis, every retained entry still links to its predecessor and is individually signature-valid; the verifier has no concept of where the chain should end. (b) Deleting an org's entire chain also verifies (empty slice → Ok). The `seq` column confirms the gap is real: it is bound in the INSERT (postgres.rs:139) and read back into AuditRow.seq (marked #[allow(dead_code)], postgres.rs:188-189), but it is NOT among the fields fed to canonical_payload_bytes (mod.rs:146-153: only id, org_id, timestamp, actor, event, payload). So seq is neither hashed nor signed and is never validated for contiguity (list() merely ORDERs BY seq ASC, postgres.rs:166). Grep across the crates found no tip/anchor/chain_length/chain_tip mechanism — only doc comments. The sole verify_chain caller is a test (auth/tests/keys.rs:350); no production verifier checks seq monotonicity either. This contradicts the explicit promise that 'the chain is the tamper-evident record of every privileged action' (keys.rs:457-458). Severity high is appropriate: the threat model the signing scheme exists to defend (DB-write-capable insider/attacker) is exactly the one that can tail-truncate or wholesale-delete the log undetectably, defeating tamper-evidence for the most security-critical records (key revocations, privileged actions). Note the bound on harm: an attacker WITHOUT the Ed25519 signing key still cannot forge or modify existing entries — the chain remains evidence against modification and reordering. The unmitigated gap is specifically truncation/deletion of the tail and full-chain deletion, the classic append-only-log truncation attack, whose standard fix (binding seq into the signed payload plus an externally-anchored/published signed tip) is absent.

- [x] **🔴 [security] Unbounded `k` in <retrievable> tag flows into SQL LIMIT (resource-exhaustion DoS)** `(pub-cache-retrieval)`  **✅ DONE in #69 (2026-06-07).**
  - **Where:** crates/retrieval/src/tags.rs:35-39; crates/retrieval/src/substitute.rs:109; crates/retrieval/src/store/postgres.rs:90-95
  - **Issue:** The `k` attribute is parsed from caller-supplied message content with `k_re ... .parse::<u32>()` and is never bounded. It flows verbatim through `top_k(store, org_id, &t.corpus, &query_emb, t.k as usize, floor)` into the Postgres query as `LIMIT $4` (bound via `i64::try_from(k).unwrap_or(i64::MAX)`). A request containing `<retrievable corpus="x" k="4000000000">...</retrievable>` asks pgvector to walk the HNSW graph and materialize up to ~4 billion rows for that org/corpus, and the results are then collected into a Vec and string-joined in `substitute`. Because the tag lives in untrusted prompt text, any caller can trigger a large-LIMIT scan per tag, and multiple tags multiply the cost. This is a cheap-to-send, expensive-to-serve amplification on the retrieval path.
  - **Action:** Clamp `k` at parse time to a sane maximum (e.g. `k.min(MAX_RETRIEVAL_K)` with MAX ~50-100) in tags.rs, and additionally clamp in top_k/substitute as defense in depth. Document the cap. Same applies to capping the number of <retrievable> tags processed per message.
  - **Verified:** The cited code is accurate: `k` is parsed from caller-supplied message content as an unbounded u32 (tags.rs:35-39, default 5, no clamp), flows verbatim through top_k (substitute.rs:109) into the Postgres `LIMIT $4` bound as `i64::try_from(k).unwrap_or(i64::MAX)` (postgres.rs:90-95), and the tag originates from untrusted request-body message content via the retrieval middleware. So an unbounded-input → SQL-LIMIT path genuinely exists, and the codebase clamps similar values elsewhere (temperature.clamp at chat.rs:1560, last.clamp at plan_history.rs:46), so a missing clamp on k is a legitimate input-validation gap.

However, the audit OVERSTATES both the mechanism and the severity, so it is downgraded from high to low:

1. Mechanism is wrong. `ORDER BY embedding <=> $3 ... LIMIT 4000000000` against an HNSW index does NOT force pgvector to "walk the HNSW graph and materialize ~4 billion rows." A LIMIT can never return more rows than exist in the matched partition; the query returns at most the number of chunks actually stored for that (org_id, corpus). The cost is bounded by the org's own corpus size, not by k.

2. Tenant isolation confines the blast radius to the caller's OWN data. org_id is taken from the authenticated ApiKeyContext and is fail-closed (middleware retrieval.rs:216-243), and the query is filtered `WHERE org_id = $1 AND corpus = $2` (postgres.rs:88). An attacker can only force retrieval over a corpus they themselves populated in their own org. There is no cross-tenant or unauthenticated amplification — contradicting the "any caller, cheap-to-send, expensive-to-serve amplification" framing.

3. Amplification is weak. Request body is capped at MAX_BYTES = 1 MiB (retrieval.rs:32,151), bounding tag count, and per-tag cost still scales only with the attacker's self-uploaded corpus.

The genuine residual concern is that all returned rows are collected into a Vec<RetrievalResult> with full text and string-joined (substitute.rs:117-121), so an org with a large corpus could pull/concat its entire corpus per tag into gateway memory — a real but self-inflicted, tenant-scoped resource concern. That warrants clamping k to a small MAX (hardening), but it is not the high-severity, attacker-amplified DoS described.

- [x] **🔴 [bug] Retrieval store has no embedding-model partitioning (cross-embedding-space corruption)** `(pub-cache-retrieval)`  **✅ DONE in #70 (2026-06-07).**
  - **Where:** crates/retrieval/src/store/postgres.rs:69-113; crates/retrieval/src/types.rs:24-34; crates/retrieval/src/embed.rs:9-26
  - **Issue:** The L2 semantic cache was deliberately hardened (backlog rv-l2-cache-correctness) to store `embedding_model` on every CacheEntry and filter lookups on it, so 'a switch in embedding models never compares vectors from different spaces' (l2.rs:65-69). The retrieval store has NO such column or filter: `Chunk` (types.rs:24) carries only org_id/corpus/doc_id and the search query is `WHERE org_id = $1 AND corpus = $2` with no model dimension. `EmbeddingClient.model` is mutable (embed.rs:13) and defaults to text-embedding-3-small, but nothing records which model produced a stored chunk. If the embedding model is ever changed (or a corpus is indexed with one model and queried after a model swap), cosine similarity is computed across incompatible vector spaces, silently degrading or corrupting retrieval ranking — the precise failure mode the cache crate calls out and guards against. This is an inconsistency between two sibling subsystems that share the same HNSW pattern.
  - **Action:** Add an `embedding_model` column to `retrieval_chunks` and `Chunk`, populate it at insert from `EmbeddingClient.model`, and add `AND embedding_model = $N` to the search query (mirroring PostgresL2Cache::lookup). Exclude NULL/legacy rows from matching.
  - **Verified:** The factual claims are all verified against the actual code. crates/retrieval/src/types.rs:24-34: `Chunk` carries only id/org_id/corpus/doc_id/chunk_idx/text/embedding/metadata — no embedding-model field. crates/retrieval/src/store/postgres.rs:84-90: search filters `WHERE org_id = $1 AND corpus = $2` with no model dimension. The migration (crates/core/migrations/0005_retrieval_chunks.up.sql) has no embedding_model column. crates/retrieval/src/embed.rs:13 confirms `EmbeddingClient.model` is a public (mutable) field defaulting to text-embedding-3-small. And the contrast is real: crates/cache/src/l2.rs:487 filters `AND embedding_model = $5` with an explicit comment that this "prevents comparing vectors from different embedding spaces." So the inconsistency between the two sibling HNSW subsystems is genuine, and the retrieval store does lack the defense-in-depth guard.

However, the severity is overstated as high. Two facts cap the realistic harm: (1) No production code path ever changes the embedding model. Every real construction is `EmbeddingClient::openai()` (cli/src/retrieval/mod.rs:22,46; core/src/middleware/retrieval.rs:104), which hardcodes text-embedding-3-small. There is no config/env to select an embedding model and nothing mutates `.model` outside tests, so the audit's triggering premise ("if the embedding model is ever changed") is hypothetical, not a current defect. (2) The schema pins `embedding   vector(1536) NOT NULL`, so any swap to a different-dimension model (e.g., text-embedding-3-large at 3072) is rejected at INSERT by Postgres — a hard error, not silent corruption. Silent cross-space corruption would require swapping to another 1536-dim model via the OpenAI `dimensions` param, which is not exposed anywhere. This is therefore a valid latent robustness/forward-compat gap and a real sibling-subsystem inconsistency worth fixing before an embedding-model becomes configurable, but it causes no harm in the current codebase and the dimension pin blocks the most damaging case. Low severity.

- [x] **🟡 [security] verify cache caches a positive result for ~60s, so a revoked key keeps working until TTL expiry** `(pub-auth-telemetry)`  **✅ DONE in #75 (2026-06-08)**
  - **Where:** public/crates/core/src/middleware/auth.rs:70-99; public/crates/auth/src/lib.rs:6-11 (documented tradeoff)
  - **Issue:** On a cold verify the ApiKeyContext is cached for ~60s keyed by blake3(token). revoke_key marks the row revoked but does not invalidate the in-process verify cache, so a compromised/leaked key that an operator revokes in response to an incident can continue authenticating for up to the positive TTL on every gateway instance. This is an intentional, documented staleness tradeoff (lib.rs:6-11, key_cache.rs), but 60s of continued access after an emergency revoke is a real incident-response weakness, and it is per-process so a multi-instance fleet has no coordinated bust.
  - **Action:** Add an explicit cache-invalidation hook (revoke_key returns the token_hash or key_id so the gateway can evict; or a small pub/sub revocation channel) and consider shortening the positive TTL for live keys or making it tier-configurable. At minimum surface the worst-case revoke-to-effect window in the security docs so operators know to also rotate upstream provider keys on compromise.
  - **Verified:** Confirmed against the cited code. The in-process verify cache stores a positive ApiKeyContext for POSITIVE_TTL_SECS=60 keyed by blake3(token) (key_cache.rs:70, 209-211; auth.rs:73,90), and a cache hit skips argon2 and is accepted (auth.rs:76-80). revoke_key (auth/src/keys.rs:467-498) only mutates the KeyStore and writes an audit row; it holds no reference to KeyVerifyCache and never calls evict — grep confirms cache.evict() appears ONLY in tests, never in any production path. The codebase's own test revoked_key_accepted_within_positive_ttl_then_rejected_after_eviction (auth.rs:525-590) asserts that a key revoked in the store still returns HTTP 200 within the positive TTL and that find_by_prefix/argon2 is NOT re-run (find_count stays at 1). So a revoked/leaked key keeps authenticating for up to 60s after an emergency revoke, per gateway instance. This is real, concrete harm to incident response. Severity is correctly medium: the window is bounded at 60s, requires a recently-verified (warm) entry, and is an explicit, documented latency/DoS-resistance tradeoff (lib.rs:6-11, key_cache.rs:28-37) with a stated future mitigation — not exploitable for privilege escalation or unbounded access, so neither high nor low.

- [x] **🟡 [security] Credentials file is briefly world/group-readable: write-then-chmod TOCTOU** `(pub-cli)`  **✅ DONE in #77 (2026-06-08)**
  - **Where:** crates/cli/src/context/store.rs:58-66 (save_credentials)
  - **Issue:** save_credentials calls std::fs::write(&p, body) and only afterward set_mode(&p, 0o600). std::fs::write creates the file at the process's default umask (commonly 0644 / 0664), so between the write and the chmod the API key is on disk readable by other local users/processes. On a multi-user host or shared CI runner this is a real window to read tt_live_* keys. ensure_dir creates the dir 0700 which helps, but the dir mode is also best-effort (.ok()) and a pre-existing ~/.tokentrimmer with looser perms is not tightened.
  - **Action:** Create the file with restrictive perms atomically: use OpenOptions with .mode(0o600) (unix) via custom open, or write to a temp file created 0600 then rename into place. Also consider re-asserting 0700 on the dir even when it already exists, and on non-unix document that the key is stored unprotected.
  - **Verified:** VERIFIED against /Users/iansimon/Developer/TokenTrimmer/public/crates/cli/src/context/store.rs. The cited code pattern is exactly as described.

- Line 64: `std::fs::write(&p, body)` creates credentials.toml; on a fresh file this uses 0o666 & ~umask (commonly 0644).
- Line 65: `set_mode(&p, 0o600)` chmods only AFTER the write completes — a genuine write-then-chmod sequence with a non-atomic window where the secret key file briefly has umask-default mode. This is a real anti-pattern; best practice is to create the file with 0o600 atomically (e.g. OpenOptions().mode(0o600)).

So the structural finding is REAL. However the reviewer OVERSTATES both the impact and one factual claim:

1. Impact overstated. The file lives inside `~/.tokentrimmer/`, which ensure_dir (lines 38-42) creates as 0700. On Unix, a directory without the group/other execute (traverse) bit prevents OTHER unprivileged users from open()-ing any file inside it regardless of that file's own mode. So during the brief 0644 window the key is NOT actually readable by other local users as long as the dir is 0700. The dir-level protection largely defeats the described window for the unprivileged-attacker threat model the finding invokes ("multi-user host / shared CI runner"). The "real window to read tt_live_* keys" framing is therefore not well supported.

2. Factual error in the finding. It claims "a pre-existing ~/.tokentrimmer with looser perms is not tightened." That is wrong: ensure_dir calls create_dir_all (idempotent no-op on existing dirs) and then set_mode(dir, 0o700) UNCONDITIONALLY on every save, so a pre-existing loose dir WOULD be re-chmod'd to 0700 (best-effort).

The legitimate residual risk is defense-in-depth: the directory chmod is best-effort (`set_mode(dir,0o700).ok()` swallows failure, line 40), so if that chmod ever fails the dir stays at umask-default (e.g. 0755) and THEN the non-atomic file window becomes exploitable. Two best-effort/non-atomic steps stacked means the security relies on an un-checked side effect. That is worth fixing (create the file 0600 atomically and/or verify dir mode), but it is hygiene/hardening rather than a confirmed exposure path. Re-graded medium -> low: the code smell is real and worth fixing, but concrete, unambiguous harm is gated behind the 0700 dir holding, and the finding's strongest impact claim plus its pre-existing-dir claim do not hold up.

### `pub-providers-a`

_Provider adapter group A (openai/anthropic/gemini/compat) is in solid shape on the core security axes the area cares about: credentials are never forwarded cross-provider (each adapter sets its own auth header — Bearer for OpenAI/compat, x-api-key for Anthropic, x-goog-api-key for Gemini — from ctx.credentials.api_key, and SecretString prevents accidental Debug leaks), the Gemini key was correctly moved out of the URL query into a header, SSRF validation (validate_provider_url) covers RFC1918/loopback/link-local/CGNAT/cloud-metadata for both IP literals and DNS-resolved hosts with an honest documented DNS-rebind caveat, and the extra_headers denylist blocks auth/host/hop-by-hop overrides. ### `pub-sdks`

_The two thin SDK wrappers (Python `tokentrimmer`, TypeScript `@tokentrimmer/client`) are small, well-commented, and correct for the common non-streaming chat path: both default base_url to the hosted gateway, lift `tt_tag` into `X-TokenTrimmer-Tag`, inject a `max_tokens=4096` default, and attach parsed `X-TokenTrimmer-*` cost metadata as `.tt`.
